# UI Integration Contract

## 展示基线

现有 UI 是唯一展示基线：

`work/company_impact_high_quality_v2_candidate/ui/index.html`

不得重构、删除或替换现有 UI。保留既有布局、导航、栏目、视觉风格和交互；只能通过数据适配层更新其展示数据。

## 既有栏目映射

| 数据域 | 写入既有栏目 | 最低要求 |
| --- | --- | --- |
| event / evidence | 事件概览、事件时间线 | 标题、时间、来源事实、状态、原文链接 |
| reasoning path | 动态传导链 | 区分来源事实、研究推断、行情验证和因果边界 |
| industry | 行业影响 | 即时、短期、中期分别陈述，保留行业 ID |
| company | 公司影响 | 公司代码、暴露机制、三阶段方向、证据与行情状态 |
| event-linked QA | 研究问答 | 保留 `event_id`，答案引用当前事件的事实、行业和公司内容 |
| market / audit | 现有详情与状态标签 | 窗口、基准、计算状态、`ABSTAIN`、缺口和审核状态 |

## 接入顺序

1. 冻结经 `validate` 通过的候选 run 和其数据版本。
2. 编写或更新适配层；不得把数据复制成与主数据脱节的第二份手工内容。
3. 进行单事件接入，保留现有十事件导航及其他事件内容不变。
4. 截图核对原页面与接入后页面：栏目顺序、文本可读性、交互、证据链接、行业—公司联动和 QA 跳转均不得退化。
5. 核对 UI 数据与 run 内事件 ID、来源证据、行情状态和 SHA/版本信息一致。
6. 用户确认单事件效果后，才批量接入其余事件。

## 兼容与边界

- 旧数据兼容：新字段缺失时显示已有的待补、数据缺失或待审核状态，不得报错、留白误导或伪造数值。
- 优先并入现有事件详情、行业、公司和研究问答区域；未获用户确认不得增加独立工作流或替换页面结构。
- UI 不得把 `NEEDS_HUMAN_REVIEW`、`formal_ready=false`、`DATA_MISSING`、`PARTIAL_CALCULATED` 或 `ABSTAIN` 弱化成已验证或因果结论。
- 行情仅展示表现或机制一致性；非 `IDENTIFIED` 的因果结论必须原样显示 `ABSTAIN`。
- 每次更新记录 run ID、数据版本、数据截止时间、验证结果与截图位置，保证可回溯。

## 不可变版本链

- 基线和每个候选版本保存原 `index.html`、版本内 `ui_data_bundle.js`、父版本、研究 run、逐事件规范化哈希及构建/验证/复现/截图 SHA。
- 既有事件标记 `FROZEN_UNDER_PREVIOUS_GATE`；规范化 JSON 哈希不得改变，也不得宣称通过新门禁。
- 新版沿用固定顺序：事件概览、研究问答、事件时间线、动态传导链、行业影响、公司影响。不得增加独立候选概览、材料完整性矩阵或重复 QA 区块。
- 人工确认前只创建 `versions/<version>/`。确认后才以 `os.replace` 原子切换稳定 bundle 和 `latest_release.json`；切换不改变研究审核、正式就绪或因果状态。
- 已冻结版本不得原地编辑，任何数据或文案改动都创建下一个递增版本。
